Benne per dins

Com s'acoblen els JSON de cada joc amb el motor Benne, què fa cada fitxer TypeScript, i fins on podem portar l'aspecte visual: escenaris pintats a l'estil de les reedicions dels clàssics de LucasArts i camins amb pujades i baixades.

Contingut del joc (JSON + lògica) Nucli narratiu (TS pur) Adaptador Benne Motor Benne (Phaser) Art (Python)
Part 1 · Arquitectura

Quatre capes, i només una sap que existeix Benne

La regla de disseny del repo: la història no sap res del motor gràfic. Tot el que és Benne viu a adapters/benne/ i al projecte Benne de cada joc. Si demà canviéssim de motor, game/ i packages/narrative-core/ no es tocarien.

Contingut

games/<joc>/game/
  • data/*.json: sales, objectes, personatges, diàlegs, missions, pistes, finals, estat inicial
  • locales/ca/: tots els textos (el JSON només porta claus)
  • logic/*.ts: regles pròpies del joc (accions amb nom)
  • test/: partides senceres en mode text

Nucli narratiu

packages/narrative-core/
  • Estat (flags, vars, memòria, relacions)
  • Avalua condicions i aplica efectes
  • Resol interaccions i diàlegs
  • No toca pantalla ni inventari: emet esdeveniments

Adaptador

adapters/benne/ + games/<joc>/adapters/benne/
  • En compilar (sync): genera fitxers Benne a partir del JSON
  • En jugar (runtime/): el pont entre els clics de Benne i el nucli

Motor Benne

packages/benne/ → còpia RO a games/<joc>/<joc>/src/engine
  • Phaser + WebGL, Vite
  • Sales, caminar, pathfinding, verbs, GUI, so, partides desades
  • BenneScript: l'API que fan servir els scripts

Dependències només cap avall: game → core, adaptador → core + game + Benne. El nucli no importa res de Benne; Benne no importa res del nucli (només hi arriba el pont, copiat dins src/game/narrative/).

Part 1 · Dos JSON per a cada sala

El JSON nostre diu què passa; el de Benne diu on és

Cada sala té dos fitxers que no es trepitgen. El nostre és lògica i textos; el de Benne és geometria i art. Els uneix l'identificador (i, quan no coincideix, mapping.json).

game/data/rooms/granja_pati.json

{
  "protagonists": ["iri", "vet"],
  "hotspots": {
    "pou": {
      "name": "sala.granja_pati.pou.nom",
      "interactions": [
        { "verb": "look",
          "if": { "flag": "bomba_llegida", "is": false },
          "lines": [{ "who": "player",
                      "text": "sala.granja_pati.pou.1" }] },
        { "verb": ["walkTo","use","open"],
          "goTo": "granja_casa" } ] } } }

Verbs, condicions (if), línies (claus de text), efectes, goTo, diàlegs, accions. Validat amb game/schemas/*.schema.json.

<joc>/src/game/rooms/granja_pati/granja_pati.room.json

{
  "size": { "width": 640, "height": 360 },
  "scrollBounds": { "x":0,"y":0,"width":640,"height":360 },
  "walkable": { "polygons": [{ "points": [...] }] },
  "hotspots": [{ "id": "pou", "points": [...],
                 "walkToPoint": {...}, "baseline": 204 }],
  "props":   [{ "id": "BG", "zIndex": 0 }, ...],
  "regions": [],
  "characters": [{ "definition": "iri/iri.character.json",
                   "x": 442, "y": 236 }] }

Polígons (caminable, clicable), props de l'atles Aseprite, personatges, regions (escala, tint), càmera. S'edita amb l'editor de sales de Benne o el genera room_designs.py.

Part 1 · En compilar

npm run benne:sync: del JSON al projecte Benne

sync.ts

Carrega el contingut del joc (tools/load-game.ts) i el valida amb el nucli (validate.ts). Si falla, no escriu res.

sync.ts → src/game/narrative/

Copia el pont (adapters/benne/runtime/*, i a sobre els fitxers de games/<joc>/adapters/benne/runtime/) i escriu content.generated.json (dades + textos) i mapping.generated.json.

benne-content.ts

Per cada diàleg nostre, un diàleg Benne amb totes les opcions aplanades (<node>__<opció>); el pont encén les que toquen. Textos de verbs i menús, botó Canvia, portada, GUI pròpies del joc.ts.

benne-content.ts → rooms/, characters/, inventory

Crea les sales, personatges i objectes que encara no existeixen, amb disposició automàtica. Afegeix coses noves a sales existents. Les coses amb visibleIf es fan props; els decor, props no clicables.

tools/*.py (Pillow)

Mentre hi ha la marca .provisional: dibuixa fons (tools/hd640/rooms/<sala>.py), sprites i icones, i ajusta la geometria del .room.json perquè el que es veu i el que es clica coincideixin.

templates/globalScript.ts

Regenera el bloc marcat de src/game/globalScript.ts: tota interacció sense gestor propi i tota entrada a sala van al pont. El que hi ha a sota de les marques es conserva.

Tot el que genera porta la marca GENERAT. El sync es nega a sobreescriure un fitxer sense la marca: el que un artista o programador toca a mà no es perd.

Part 1 · En jugar

Un clic, de punta a punta

Exemple: el jugador fa «Usa clau anglesa amb palanca».

Benne · RoomScene

Hit-test del polígon del hotspot, camina fins al walkToPoint (pathfinding sobre el polígon caminable), resol el verb.

Benne · globalScript.ts

Cap script de sala no la gestiona → fallbacks.onUseItem.

runtime/narrative.script.ts · routeInteraction

Tradueix ids de Benne als nostres amb el mapping (fabrica_cambra-hotspot-palanca → palanca) i crida el nucli.

narrative-core · Narrative

Busca la interacció al JSON de la sala, avalua els if (consulta el món via WorldPort: inventari, sala, protagonista), aplica efectes, executa accions de game/logic. Retorna un InteractionResult (línies, diàleg, sala, canvi de protagonista) i emet NarrativeEvents.

runtime/narrative.ts

Escolta els esdeveniments: giveItem/takeItem → inventari Benne; stateChanged → desa l'estat dins la partida de Benne i mostra/amaga props condicionals; la resta → esdeveniments Benne narrative:<tipus>.

runtime/narrative.script.ts · playResult

Executa el resultat a Benne al llarg del temps: player.say, dialogs.x.start(), player.switchTo, rooms.x.goTo().

Els scripts de sala de Benne (*.room.ts) només calen per a coses visuals: animacions, moviments, càmera. La lògica és sempre al JSON o a game/logic/, i per això els tests de partida corren sense navegador (headless.ts + MemoryWorld).

Part 2 · Aspecte

Podem arribar a l'estil de les reedicions?

Comparant les dues captures, la diferència no és només de pinzell. He mirat què fa servir avui Aigua Verne (27 sales) i què ofereix el motor.

Resposta curta: el motor no és el límit. L'art sí, però no és l'únic que cal.

Només millorant l'art (fons pintats a 640×360) guanyaríem molt, però el joc continuaria semblant pla: la sensació de la primera captura ve igualment de l'escala per profunditat, l'scroll, el parallax i el tint per zones, que Benne ja té i no fem servir. Això és feina de disseny de sala, no de motor, i es pot començar ja amb l'art actual.

Pas 1 · Sense tocar el motor

  • Regions d'escala a totes les sales exteriors (i scaleWalkSpeed).
  • Alguna sala ampla (p. ex. 1280×360) amb scroll i 2–3 capes de parallax.
  • Regions de tint: ombra sota els arbres, llum càlida a prop del foc.
  • Més props d'ambient animats per sala.
  • Afegir-ho a room_designs.py perquè el sync ho generi.

Pas 2 · Art pintat

  • Fons pintats per una persona (o pintats sobre la base que genera Python). El pipeline procedural no arriba a aquest acabat.
  • Pujar la resolució (1280×720 o 1920×1080) és possible: ja hi ha precedent (migra_resolucio.py, 480→640). Toca coordenades, GUI i fonts.
  • Revisar el filtre del shader de perspectiva (ajusta a la graella de píxels; amb art suau cal filtre lineal).
  • El cost gros són els personatges: a alta resolució, cada animació (caminar ×4 direccions, parlar, agafar) es dibuixa a mà. Això, més que els fons, decideix si és viable.
Part 3 · Relleu

Pujades i baixades

En una aventura 2D no hi ha alçada real: la pujada és una il·lusió que fan tres coses juntes. Benne en té dues de sèrie; la tercera és un canvi petit.

PeçaEstatCom
Camí que puja per la pantallaja hi ésEl polígon caminable pot tenir qualsevol forma. Una franja estreta que segueix el camí pintat obliga el pathfinding a pujar per on toca, fent ziga-zaga si cal. baseline als props perquè el turó tapi el personatge quan és darrere.
Escala segons la distànciaja hi ésregions[] amb scaleTop/scaleBottom. Compte: l'escala només depèn de la Y dels peus. Un turó vist de costat (pujar sense allunyar-se) necessita una regió amb scaleTop = scaleBottom; un camí que s'allunya, una regió que encongeix. Diverses regions encadenades fan un turó que primer puja i després s'allunya.
Anar més a poc a poc pujantcal un canvi petitscaleWalkSpeed lliga la velocitat a l'escala, no al pendent. Proposta: un camp walkSpeed (multiplicador) a RoomRegionData, llegit on ja es llegeix scaleWalkSpeed. Va a packages/benne i val per a tots els jocs.
Sales altes amb càmera verticalja hi éssize.height > 360 i scrollBounds: la càmera segueix la protagonista amunt i avall (un penya-segat, una escala llarga).
Postura de pujada (cos inclinat)opcionalAmb setOutfit() (canvi nostre al motor) es poden tenir animacions pujaWalkL… i activar-les en entrar a la regió (esdeveniments d'entrada/sortida de regió). Les reedicions gairebé mai ho fan.
El que dona més sensació de relleu, per ordre

1) que el fons dibuixi el pendent i el camí, 2) que el polígon caminable el segueixi exactament, 3) l'escala per regions, 4) les oclusions amb baseline. La velocitat és la cirereta. Les tres primeres ja es poden fer avui amb room_designs.py: el que falta és afegir-hi un camp regions perquè el sync les escrigui al .room.json.
